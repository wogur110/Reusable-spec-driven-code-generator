# CHG-004 explicit client presence

This registered extension overrides DIRECTORY's heartbeat-only presence and blanket prohibition on all requests in Development offline mode only as described here. All old message/receipt objects, stores, selectors, session limits and failure semantics remain. The user explicitly requested server status changes by client communication when choosing Offline/Online, without other users sending messages. Web layout changes are specified in TYPESCRIPT.md.

## Server contract

Add POST /api/v1/presence, no query, exact JSON {"username":"alice","online":false}. Validate exact fields/object (400 INVALID_FIELDS, field null), username (400 INVALID_USERNAME, field username), then strict JSON boolean online (400 INVALID_PRESENCE, field online). Standard framing/media/duplicate-key/deadline errors apply. Other methods return 405, Allow: POST. On success return 200 exactly the requested {username,online}; no session token or storage migration.

Under the same store lock, create the known username if necessary. online=false sets an explicit-offline latch and clears its heartbeat time. online=true clears the latch and records a current heartbeat. Repeated calls are idempotent membership/state updates. GET users shape stays exactly {users:[{username,online}]}: online is false while explicitly offline, otherwise true only for a heartbeat younger than 15 seconds. POST users remains compatible and refreshes heartbeat only if the username is not explicitly offline. Thus a late old heartbeat, message addressed to this user, outgoing message, receipt report, GET, or operator refresh can NEVER resurrect an explicitly offline user. Only POST presence online=true releases the latch. Once explicitly online, normal heartbeat expiry still applies to crashes or genuine network loss. State clears with the server session. One supported active client per username; unauthenticated local demo claims, not account/security guarantees.

No presence operation acknowledges messages, clears queues, or changes message/activity counts. Server Users status is automatically refreshed within one second. Explain visibly: a communicated Offline choice applies immediately; heartbeat timeout handles uncommunicated disconnections. Keep the exact Online/Offline labels and all original control identifiers.

## Client transition rules (Python GUI/machine and browser)

Keep ONE serialized network scheduler, with at most one active request. On an online-to-offline selection, set local transport offline immediately, keep enqueue/editing responsive, mark directory stale, and stop scheduling ordinary messaging, receipts, announcements and directory requests. Permit exactly one final POST presence online=false with a two-second total deadline even though local transport is offline. This narrow exception communicates the user's choice; it is not permission to send queued messages. Prior in-flight work finishes or reaches its original deadline, then the notification has priority over all remaining cycle work and sleep. Healthy explicit-offline observation must finish within eight seconds including an existing five-second request and server GUI refresh; do not wait for the 15-second heartbeat TTL. Do not abort an old heartbeat then start an overlapping notification: serialize them. Repeated selection of the same mode must not start repeated offline notifications. After that one bounded attempt, no further API traffic while offline. Offline startup/login never requires network or sends a notification merely for starting offline.

On identity login/restoration while online, and each offline-to-online transition, schedule POST presence online=true before the next ordinary cycle. Retry an unconfirmed online notification once at the start of each online cycle, without blocking that cycle's messaging if it fails. Once confirmed, normal POST users heartbeats suffice until another transition or identity reset. Each presence request has a two-second deadline, making a retry cycle at most 18 seconds of network work plus the existing one-second delay. Existing message deadlines remain five seconds; other auxiliary deadlines remain two seconds. A valid core CURSOR_INVALID still pauses network work until reset. A successful presence call does not clear core errors or change message delivery states.

Transport/UI and machine commands return promptly; never block the GUI thread or event loop waiting for the final notification. Coalesce transitions before dispatch to the latest desired mode. If the desired mode changes during a presence call, finish/deadline that call and prioritize the latest intent afterward; a stale success must not confirm the new intent. Every call/response is bound to the identity/reset generation and mode revision. On reset/close discard pending work and stale responses, honoring existing reset/shutdown bounds; shutdown/unload notification is not required. New identity login must not execute an old identity's queued notification. Preserve atomic reset readiness: clear all rendered old message/directory rows before exposing enabled login controls. Never resurrect old rows after login renders.

A failed offline notification leaves local transport offline and queued messages durable; do not retry while offline or claim the server confirmed it. Heartbeat expiry handles the uncommunicated disconnect. On reconnect send the explicit online update again even if a previous offline reply was lost. Presence endpoint errors never dequeue/fail messages or modify persisted outbox error fields. Validate exact response keys, username and boolean equal to the request. No new SQLite/IndexedDB fields, caches or schema version.

## Presence report observation

Add app.widgets['presence-status'] Label in Python GUI and data-testid=presence-status in browser, text exactly unknown/pending/confirmed/error. unknown before an intent has been attempted, pending for the current scheduled/in-flight intent, confirmed only for its valid matching server reply, error for its failure. Add visible explanatory text that this reports the selected mode to the server and real network loss may delay server Offline status. Keep the transport-mode control as the local desired mode. Stale results cannot replace a later mode's status; reset returns unknown. Machine command/status schemas are unchanged; the machine interface drives the identical production transition logic.
